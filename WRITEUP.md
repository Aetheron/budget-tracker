My task was to build a lightweight Personal Budget Tracker using React and Typescript for the frontend and Node.js for the backend. The spec defined the endpoints and the required features, including a transaction list, a form to add transactions, a summary element, and search capabilities. The spec noted that a monorepo with /client and /server directories for the frontend and backend was sufficient, and I adopted this architecture for the project because the app is intended to be run locally and not deployed to a hosted environment.
API calls to the backend are handled with server actions for several reasons. First, it ensures that any private keys or other sensitive environment values are not exposed to the client, which would jeopardize security. Second, server actions typically run faster as they have more computing power available to them than the client’s browser. Third, they separate concerns by collecting similar functions – requests to the backend – in a single location.
I chose to use the CSS framework Tailwind for styling the app. In conjunction with Tailwind Plus, it allows me to quickly create modern looking, responsive, and attractive UI while spending very little time designing.
For the dev experience, I used ESLint and Prettier for format code on save. I also included the Organize Imports plugin for Prettier to automatically sort import statements and remove unused ones. This keeps code clean and consistent throughout the project and aids in readability.
My AI usage consisted of both inline suggestion completion and agent conversations with GitHub Copilot in VSCode. Inline suggestions were useful for scaffolding the API verb handlers and endpoints in the backend by looking at calls made by the frontend. I was also able to add the type definition for the data model with an inline suggestion.
I used agent conversations for thinking through some design decisions and debugging issues. For example, when I was creating the update API route, I was curious if AI would recommend sending the entire transaction object over the wire, or just the three fields that can be updated. My thought was that the unnecessary extra body size of extra fields, even if it is small, would be better eliminated. AI recommended I change the API endpoint from PUT to PATCH and go with only sending updated fields. Because the spec defined the update endpoint as a PUT request, I created two handlers for the /api/transactions/:id endpoint: one for PUT requests and one for PATCH requests. The PUT verb updates the transaction wholesale and requires all fields. The PATCH verb accepts a subset of fields and updates those.
I chose to add inline editing of transactions as my enhancement. When the user clicks the edit button on a transaction line item in the transactions table the amount, description, and category values become editable by becoming input elements. When editing is finalized, the new values appear in the transaction row and the budget summary values are updated. I chose this enhancement because it makes the UX cleaner. Instead of the user’s attention being directed to a new page or window for data that they have already seen, the user can edit values right where they appear. This keeps them focused on the current task and reduces UI friction.
With some more time, I would like to add autocompletion to the category input so that users can choose from previously entered category options. This would prevent user errors like misspelling categories and would speed up the process of entering categories by not requiring the user to enter the full category name each time.
